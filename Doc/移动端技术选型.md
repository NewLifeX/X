# NewLife 移动端 .NET 技术栈分层与选型分析

> 版本：v2 | 数据截止：2026-10-17
> 适用范围：NewLife.Core 移动端兼容性验证、NewLife 系列未来移动 App 选型
> 关联：`Samples/MobileSmoke/`、`.github/workflows/mobile.yml`

## 结论先行

1. **先分层，再谈选型**：Android/iOS 上的 .NET 技术栈分为“运行时/平台绑定 → 基础库 → UI 框架 → 应用架构”四层。Xamarin、.NET for Android/iOS、MAUI、NewLife.Core 不在同一层，直接比较会混乱。
2. **Xamarin.Android/iOS 与 .NET for Android/iOS 是同一层的新旧版本**：前者是独立 Xamarin SDK（Mono 运行时、旧项目格式、2024-05-01 结束支持）；后者是并入 .NET 的现代版本（`net10.0-android` / `net10.0-ios`，随 .NET 生命周期支持）。
3. **Xamarin.Forms 与 .NET MAUI 是 UI 层的新旧版本**：MAUI 不是 .NET for Android/iOS 的替代品，而是跑在 .NET for Android/iOS 之上的 UI 框架。
4. **在 .NET 移动 UI 层，MAUI 是事实主栈**：NuGet 下载量、Stack Overflow 问答量都明显领先 Avalonia/Uno；原生 .NET UI 是第二条现实路径；Avalonia 桌面强、移动弱；Uno 偏 WinUI 企业；Xamarin.Forms 已 EOL。
5. **NewLife.Core 是基础库，不是 UI 框架**：它的移动端验证应放在 .NET for Android/iOS 这一层，用原生薄壳直接引用 Core；UI 框架选型不应影响 Core 的兼容性结论。

## 1. 先理清层次：基础程序 vs UI

### 1.1 四层模型

| 层 | 作用 | 代表技术 | 与 NewLife 的关系 |
|---|---|---|---|
| 运行时/平台绑定 | 让 C# 跑在 Android/iOS 上，暴露平台 API | .NET for Android / .NET for iOS（Mono/CoreCLR，iOS AOT）、Xamarin.Android/iOS（旧） | Core 的宿主 |
| 基础库 | 日志、配置、网络、序列化、缓存等 | BCL、NewLife.Core、NewLife.XCode | 本次验证对象 |
| UI 框架 | 界面、交互、导航 | 原生 Android Views/UIKit、.NET MAUI、Avalonia、Uno、Blazor Hybrid、Xamarin.Forms（旧） | 与 Core 解耦 |
| 应用架构 | MVVM、Shell、DI、模块化 | CommunityToolkit.Mvvm、MAUI Shell、Prism 等 | 业务 App 选择 |

```text
Android / iOS
  └─ .NET for Android / .NET for iOS   ← 运行时 + 平台绑定（Xamarin.Android/iOS 的现代版本）
      ├─ BCL + NewLife.Core            ← 基础库（本次验证对象）
      └─ UI 框架
          ├─ 原生 .NET UI（Android Views / UIKit）
          ├─ .NET MAUI
          ├─ Avalonia
          ├─ Uno Platform
          └─ Blazor Hybrid
```

**关键点**：MAUI、Avalonia、Uno、Blazor Hybrid 最终都跑在 .NET for Android/iOS 上；它们之间是 **UI 框架层**的竞争，不是“基础程序”的竞争。

### 1.2 Xamarin 与 .NET for Android/iOS 的区别

| 维度 | Xamarin.Android / Xamarin.iOS | .NET for Android / .NET for iOS |
|---|---|---|
| 时代 | 2011–2024，独立 Xamarin SDK | .NET 6+ 起并入 .NET |
| 项目格式 | 旧 MSBuild（ToolsVersion 4.0），`TargetFrameworkVersion vX` | SDK-style，`net10.0-android` / `net10.0-ios` |
| 运行时 | Mono | Android：Mono/CoreCLR（可选 NativeAOT）；iOS：AOT |
| 平台 API | C# 绑定 Android/iOS API | 同一套绑定的现代版本 |
| 支持状态 | 2024-05-01 结束支持 | 随 .NET 生命周期支持 |
| 与 UI 的关系 | Xamarin.Forms 是旧 UI 层 | .NET MAUI 是新 UI 层，跑在其上 |

一句话：

- **Xamarin.Android/iOS → .NET for Android/iOS**：地基换新（同一层）。
- **Xamarin.Forms → .NET MAUI**：楼上 UI 换新（同一层）。
- **Xamarin（泛指）≠ MAUI**：Xamarin 是“旧时代品牌”，既包含地基也包含 UI；MAUI 只是新 UI 层。

### 1.3 常见混淆点

| 容易混淆的说法 | 实际情况 |
|---|---|
| “Xamarin 和 MAUI 是两种并列的框架” | Xamarin.Forms 与 MAUI 是 UI 层的新旧版本；Xamarin.Android/iOS 与 .NET for Android/iOS 是地基的新旧版本 |
| “MAUI 替代了 .NET for Android/iOS” | 不是。MAUI 依赖 .NET for Android/iOS；不用 MAUI 也可以直接用原生 .NET UI |
| “Avalonia / Uno 和 MAUI 是不同地基” | 不是。它们都是 UI 框架，最终都跑在 .NET for Android/iOS 上 |
| “NewLife.Core 和 MAUI 是可比较的框架” | 不是。Core 是基础库，MAUI 是 UI 框架，不同层 |
| “基础程序就是 UI” | 基础程序 = 运行时 + 基础库；UI = 界面框架。两者可以独立选择 |

### 1.4 对 NewLife.Core 的意义

- Core 是基础库，不依赖 UI 框架；
- 移动端验证应使用 .NET for Android/iOS 的原生薄壳，直接引用 Core；
- MAUI/Avalonia/Uno 的选型不改变 Core 的兼容性结论；
- 如果未来要验证“MAUI 用户真实路径”，可以再加一个 MAUI 宿主，但它不能替代原生壳。

## 2. .NET 移动技术栈全景

### 2.1 运行时/平台绑定层

**代表**：`net10.0-android` / `net10.0-ios`、`dotnet new android` / `dotnet new ios`。

- **.NET for Android**：C# + Android 平台 API，Mono/CoreCLR 运行时，可选 NativeAOT；使用 Android SDK/JDK 构建。
- **.NET for iOS**：C# + iOS 平台 API，iOS 要求 AOT；构建/签名需要 macOS。
- **Xamarin.Android/iOS**：旧版本，已 EOL；只用于维护旧项目。
- 这一层提供运行时、平台绑定、AOT/裁剪、打包；不直接面向业务 UI。

### 2.2 基础库层

- BCL（`System.*`）；
- NewLife.Core、NewLife.XCode、NewLife.Remoting 等；
- 这一层与 UI 框架无关；同一份 Core 可以被 MAUI、Avalonia、Uno、原生 UI 引用。

### 2.3 UI 框架层

| 技术 | 形态 | 适用场景 |
|---|---|---|
| 原生 .NET UI | C# + Android Views/XML 或 UIKit/Storyboard | 设备能力重、性能敏感、薄封装原生 SDK、类库验证 |
| .NET MAUI | 官方跨平台 XAML/C#，单项目多目标 | 业务 App、CRUD、内部工具 |
| Avalonia | 跨平台 XAML/Skia，桌面优先 | 桌面为主、顺带移动 |
| Uno Platform | WinUI XAML 跨平台 | WinUI/UWP 企业迁移 |
| Blazor Hybrid | MAUI 宿主 + WebView + Razor | Web/Blazor 团队 |
| Xamarin.Forms | 旧跨平台 UI，EOL | 仅遗留维护 |
| PWA / Blazor Web | Web App，非原生 | Cube 管理后台、CRUD |

### 2.4 应用架构层

- MVVM（CommunityToolkit.Mvvm）、Shell/导航、DI、模块化；
- 这一层是业务 App 的组织方式，不影响 Core 的移动兼容性。

## 3. .NET 移动 UI 框架的采用度

### 3.1 口径说明

- 没有权威的“.NET 移动 UI 框架装机量/收入份额”；
- 使用 NuGet 下载、Stack Overflow 标签、GitHub stars 作为代理；
- NuGet 是累计下载，包含 CI/重复还原，不等于用户数；
- Stack Overflow 标签是累计问题量，老技术天然占优；
- GitHub stars 代表关注度，不代表生产采用；
- 结论是方向性的，不是精确市占率。

### 3.2 数据（2026-10-17）

| 技术 | NuGet 总下载 | Stack Overflow 标签 | GitHub stars | 备注 |
|---|---:|---:|---:|---|
| .NET MAUI | Microsoft.Maui.Controls 26,737,363 | maui 8,679 | 23,322 | 官方跨平台 UI |
| Avalonia | Avalonia.Android 455,608；Avalonia.iOS 290,022；Avalonia 24,169,947 | avaloniaui 596 | 31,664 | 桌面强，移动包小 |
| Uno Platform | Uno.WinUI 11,552,527 | uno-platform 402 | 10,080 | 含桌面/Web/移动 |
| Xamarin.Forms | 86,235,061 | xamarin.forms 34,573 | — | 历史累计，EOL |
| 原生 .NET UI | 无独立包 | xamarin.android 18,773；xamarin.ios 16,590 | — | 旧标签含 Xamarin 时代 |
| Blazor Hybrid | 包含在 MAUI | blazor 15,515（非 Hybrid 专属） | — | Web 团队 |
| MAUI 生态 | CommunityToolkit.Maui 10,056,783 | — | — | MAUI 活跃度 |

### 3.3 解读

- **MAUI 是 .NET 移动 UI 层的事实主栈**：`Microsoft.Maui.Controls` 下载量约为 Avalonia 移动包（Android+iOS 合计）的 35.8 倍；Stack Overflow 标签约为 Avalonia 的 14.6 倍、Uno 的 21.6 倍。
- **原生 .NET UI 是第二条现实路径**：没有跨平台 UI 包，但适合设备能力重/性能敏感场景；旧 Xamarin 标签说明历史上使用量很大，现代 .NET 原生 UI 没有独立标签可精确统计。
- **Avalonia**：GitHub 关注度高，但移动包下载量小，说明主要采用在桌面；移动端是延伸选项。
- **Uno**：WinUI/企业场景有价值，但社区规模小。
- **Xamarin.Forms**：累计下载/问答量仍大，是历史积累；EOL 后不应作为新项目选择。
- **Blazor Hybrid**：没有独立包/标签，不能从 `blazor` 标签推断 Hybrid 移动采用；它属于 MAUI 宿主的一种 UI 方式。
- **没有“.NET 移动 UI 份额”权威数字**；上表只能说明相对量级和趋势。

## 4. UI 框架对比

### 4.1 .NET MAUI

**定位**：Microsoft 官方跨平台 UI 框架，Xamarin.Forms 的继任者，随 .NET 年度发布。

**支持平台**：Android、iOS、Mac Catalyst、Windows；Tizen 由 Samsung 提供社区支持。

**优点**

- 单项目、单 C#/XAML 代码库覆盖 Android/iOS/桌面；
- MVVM、Shell、依赖注入、Handler 架构、热重载、Visual Studio / VS Code 工具链完整；
- 官方支持周期明确，生态最大（NuGet、问答、第三方控件、CommunityToolkit）；
- 对 NewLife 这类 C# 业务系统，团队学习成本最低。

**缺点/风险**

- 跨平台抽象带来包体、启动和内存开销；
- 复杂 UI、平台特有能力仍要写 Handler/平台代码；
- 版本节奏跟随 .NET，年度大版本升级需要跟进；
- iOS 构建需要 networked Mac；
- 部分控件/性能细节仍不如原生。

**适用场景**：业务 App、表单/CRUD、内部工具、需要一套 C# 代码覆盖多端的团队。

**构建要求**：.NET 10 SDK + MAUI/Android/iOS 工作负载；Android SDK/JDK；iOS 需要 Mac。MAUI 10 最低支持 Android 5.0（API 21）、iOS 12.2（MAUI Blazor 为 Android 7.0 / API 24、iOS 16.4）。

**支持/许可**：MIT；.NET MAUI 10 官方支持至 2027-05-11（MAUI 9 已于 2026-05-12 结束支持）。

### 4.2 原生 .NET UI（.NET for Android / .NET for iOS）

**定位**：C# 直接调用 Android/iOS 平台 API，UI 使用原生 Activity/XML 或 UIKit/Storyboard。

**支持平台**：Android；iOS（同族还包括 tvOS、macOS、Mac Catalyst）。

**优点**

- 完整平台 API 访问，最少抽象层；
- 启动、包体、性能最接近原生；
- 适合薄封装原生 SDK、设备能力重的场景；
- **最适合做类库的运行时验证**：没有 UI 框架干扰，问题能定位到 Core 或平台本身。

**缺点/风险**

- Android/iOS 两套 UI，代码复用低于 MAUI；
- 需要平台知识；
- iOS 构建需要 Mac；
- 业务界面开发效率低于 MAUI。

**适用场景**：蓝牙/BLE、相机、传感器、后台服务、音视频、性能敏感应用、原生 SDK 封装、Core 冒烟测试。

**构建要求**：`net10.0-android` / `net10.0-ios` 工作负载；Android SDK/JDK；iOS 需要 Mac。

**支持/许可**：随 .NET 生命周期；MIT。

### 4.3 Avalonia UI

**定位**：跨平台 XAML + Skia 渲染框架，桌面优先，11+ 提供 Android/iOS 支持。

**支持平台**：Windows、macOS、Linux、Android、iOS、WebAssembly。

**优点**

- 桌面端成熟，单一 XAML 代码库；
- 自绘 UI，视觉一致性和自定义能力强；
- MVVM、商业支持、MIT 许可；
- 对已有 Avalonia 桌面团队，移动端是自然延伸。

**缺点/风险**

- 移动端成熟度和生态明显弱于 MAUI：`Avalonia.Android` 总下载约 45.6 万、`Avalonia.iOS` 约 29 万，而 `Microsoft.Maui.Controls` 约 2674 万；
- 移动端平台集成、控件和文档相对少；
- 自绘带来包体/启动成本；
- iOS 构建同样需要 Mac。

**适用场景**：桌面为主、顺带移动；自绘/高度定制 UI；已有 Avalonia 技术栈。

**构建要求**：Android/iOS 工作负载 + Android SDK/JDK；iOS 需要 Mac。

**支持/许可**：MIT + 商业支持可选。

### 4.4 Uno Platform

**定位**：把 WinUI 3 XAML 带到 Android、iOS、WebAssembly、macOS、Linux、Windows。

**优点**

- WinUI/UWP 技能和代码可复用；
- 单 XAML 代码库覆盖多端；
- 适合企业 WinUI 存量迁移；
- Apache-2.0，商业支持可选。

**缺点/风险**

- 框架复杂度和学习曲线较高；
- 移动端性能/包体不占优；
- 社区规模较小（GitHub 约 1.0 万 stars，Stack Overflow 约 402 个问题）；
- iOS 构建需要 Mac。

**适用场景**：WinUI/UWP 企业应用跨平台、Windows 优先的行业软件。

**构建要求**：.NET 工作负载；Android SDK/JDK；iOS 需要 Mac。

**支持/许可**：Apache-2.0 + 商业支持。

### 4.5 Blazor Hybrid（MAUI Blazor）

**定位**：MAUI 宿主 + `BlazorWebView`。Razor 组件在 .NET 进程中运行，UI 渲染到内嵌 WebView，通过本地 interop 访问原生能力。

**支持平台**：通过 MAUI 宿主覆盖 Android、iOS、Mac Catalyst、Windows；也可用于 WPF/WinForms 桌面宿主。

**优点**

- 复用 Web/Blazor 技能、组件库和开发流程；
- 表单/内部工具开发快；
- Razor 组件可直接调用 .NET 与原生能力，不是浏览器 WebAssembly。

**缺点/风险**

- WebView 的性能、内存和滚动手感不如原生；
- 复杂动画、手势、图形密集场景不理想；
- 仍依赖 MAUI 与 Mac 构建 iOS；
- 调试链路比纯原生多一层。

**适用场景**：Web 团队、表单型内部应用、已有 Blazor 组件库、需要快速交付的管理端。

**构建要求**：同 MAUI；MAUI Blazor 最低 Android 7.0（API 24）、iOS 16.4。

**支持/许可**：随 .NET / ASP.NET Core；MIT。

### 4.6 PWA / Blazor Web（非原生）

**定位**：可安装的 Web App，不是原生包；也可作为 Cube 管理后台的移动端形态。

**优点**

- 一套代码覆盖 Android/iOS/桌面，更新即时；
- 不需要 Mac、不需要应用商店审核；
- 成本最低，适合 CRUD、表单、报表、内容管理；
- 与 NewLife.Cube 的 ASP.NET Core 后端天然契合。

**缺点/风险**

- 设备 API 受限（蓝牙、NFC、后台定位、部分推送、文件系统）；
- 离线/存储能力有限；
- 性能和动画不如原生；
- iOS 对 PWA 的限制比 Android 更多；
- 无法覆盖需要上架/品牌分发的场景。

**适用场景**：Cube 管理后台、内容/CRUD、内部系统、先用 Web 验证需求再决定是否做原生。

**构建要求**：现有 ASP.NET Core/Cube 技术栈，无移动工具链。

**支持/许可**：Web 标准，无框架锁定。

### 4.7 Xamarin.Forms（EOL）

- Xamarin.Android、Xamarin.iOS、Xamarin.Forms 已于 **2024-05-01** 结束支持；
- .NET for Android / .NET for iOS 是其现代替代；Xamarin.Forms 的替代是 .NET MAUI；
- 旧项目应迁移到 MAUI 或原生 .NET；
- 不建议新项目使用。

## 5. 选型决策树

```text
是否必须做成原生 App？
├─ 否 → PWA / 响应式 Web / Blazor Web（Cube 后台、CRUD、内部系统）
└─ 是
   ├─ UI 以表单/CRUD/内部工具为主？
   │  ├─ 是 → .NET MAUI（默认候选）
   │  └─ 否 → 继续
   ├─ 设备能力重/性能敏感/需要薄封装原生 SDK？
   │  ├─ 是 → 原生 .NET UI（.NET for Android / .NET for iOS）
   │  └─ 否 → 继续
   ├─ 桌面优先、顺带移动？ → Avalonia
   ├─ WinUI/UWP 企业存量？ → Uno Platform
   ├─ 团队以 Web/Blazor 为主？ → Blazor Hybrid（MAUI 宿主）
   └─ 已有 Xamarin？ → 迁移 .NET MAUI（Forms）或原生 .NET
```

补充约束：

- **iOS 构建**：以上所有 .NET UI 方案都需要 macOS；没有 Mac 时优先 macOS CI。
- **真机**：iOS 真机还需要 Apple 账号/签名；模拟器不需要。
- **不要只看下载量/Stars**：份额高不等于适合你的团队和场景；POC 验证性能、包体、设备能力和维护成本更重要。

## 6. 对 NewLife 的建议

### 6.1 NewLife.Core 的移动端验证

- **用原生 Android/iOS 薄壳 + 共享冒烟库**，不绑定 MAUI/Avalonia/Uno；
- 目的：验证 Core 的 `net10.0` 资产在 Mono/AOT/裁剪下的行为，而不是验证某个 UI 框架；
- 用例覆盖：平台信息、日志、配置、缓存、定时器、JSON/二进制序列化、TCP/HTTP/WebSocket 回环、安全加密、归档、对象容器、动态能力降级；
- Android：真机验收 + API 36 模拟器回归；iOS：GitHub Actions `macos-26` 模拟器；
- Release + 裁剪/AOT 作为门禁；Debug 只用于快速定位。

已知限制（截至本次真机验证）：

- Android/iOS 的 `MachineInfo` 只填充基础字段，`Memory` 可能为 0，平台分支待补（见 `Doc/功能清单.md` 的 IMP-25）；
- `ProcessHelper` 在受限平台可能抛 `PlatformNotSupportedException`，冒烟用例标记 SKIP；
- `PluginHelper` 动态加载在 AOT 下按设计不支持，冒烟用例验证其抛出明确异常。

### 6.2 未来 NewLife 移动 App

- **业务 App 默认候选 MAUI**：表单/CRUD/内部工具/多端覆盖，C# 团队效率最高；
- **设备密集型下沉原生**：BLE、相机、传感器、后台服务、音视频、性能敏感场景；
- **Cube 管理后台优先 PWA/响应式 Web**：移动端访问管理后台通常不需要原生 App；
- **Avalonia/Uno 只在特定约束下选**：桌面优先或 WinUI 企业存量，不作为 NewLife 业务 App 的默认；
- **Blazor Hybrid 适合 Web 团队**：已有 Blazor 组件库时收益最大。

### 6.3 iOS 构建策略

- 没有 Mac：用 GitHub Actions `macos-26`（已确认 Xcode 26.6 + .NET 10.0.400）跑模拟器；
- 有 Mac：本地模拟器 + 真机调试；
- 真机分发需要 Apple 开发者账号/签名；库级验证用模拟器即可；
- 不要因为“Windows 能编译 iOS 类库”就误以为能在 Windows 运行 iOS App。
