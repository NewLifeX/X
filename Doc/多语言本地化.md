# 多语言本地化

NewLife.Core 的异常与日志共享一套**编译期生成**的多语言表。默认跟随当前上下文语言，缺翻译自动回退英文；不依赖 resx 与卫星程序集，单 DLL、原生支持 AOT。

## 1. 语言选择

| 设置 | 作用 |
|---|---|
| `CultureInfo.CurrentUICulture` | 默认语言来源。ASP.NET Core 启用 `RequestLocalization` 时按请求变化 |
| `Localization.Culture` | 强制指定异常与常规文本语言；`null` 表示跟随 `CurrentUICulture` |
| `Localization.LogCulture` | 单独固定日志语言；`null` 表示跟随 `Culture` / `CurrentUICulture` |

```csharp
// 全站中文
Localization.Culture = new CultureInfo("zh-CN");

// 启用请求语言识别时，让日志保持英文
Localization.LogCulture = new CultureInfo("en-US");
```

## 2. 使用

### 异常

```csharp
// XException 构造器自动翻译，调用点无需改动
throw new XException("Session {0} is closed.", sessionId);

// 其它异常类型显式翻译
throw new InvalidOperationException(Localization.Translate("Session {0} is closed.", sessionId));
```

### 日志

```csharp
// Logger.Format 统一翻译，调用点无需改动
XTrace.WriteLine("Session {0} is closed.", sessionId);
```

> 日志使用**格式字符串 + 参数**，不要用字符串插值（`$"..."`）。插值后模板已展开，无法再按原文查表。

### 2.1 不要把英文短语当参数

模板按**整句**查表，参数本身不会翻译。把英文状态词或短语作为 `{n}` 参数插进已翻译的模板，会得到中英混排（如“配置文件 xxx failed to load”）。正确做法：

```csharp
// ✅ 推荐：按语义拆成多条完整英文句子，各自作为词条
var msg = exists
    ? "The configuration file {1} of {0} failed to load; overwriting with the default configuration."
    : "The configuration file {1} of {0} is missing; overwriting with the default configuration.";
XTrace.WriteLine(msg, typeName, file);

// ✅ 短语本身有限且可枚举时：对短语单独查表，并为全部语言补齐词条
XTrace.WriteLine("Result: {0}", L.T("random"));

// ❌ 状态词只作为参数传入，译文模板里仍是英文
XTrace.WriteLine("The configuration file {1} of {0} is {2}; ...", typeName, file, "missing");
```

## 3. 新增内置语言

在 `NewLife.Core/Locales/` 新增 `<culture>.yml`，每行一条：

```yaml
"Session {0} is closed.": "会话 {0} 已关闭。"
```

规则：

- 键必须是**英文原文**，且与代码中的模板完全一致；
- 占位符集合（`{0}`、`{1}`…）必须与英文一致，否则**编译失败**；
- 同一文件内键重复、语法错误同样编译失败；
- 缺失翻译不报错，运行期回退英文；
- 新增键必须**同步补进全部语言文件**，否则 `check-locales.ps1` 报"缺少键"。

语言文件由随 `NewLife.Core` 主包分发的源生成器在编译期生成：全部语言共享一份键表，译文以 Deflate 压缩的字节数组内嵌，首次使用时解压建字典。生成物不随包分发。

### 3.1 覆盖范围与校验

**纳入词表**（运行时可见的消息）：异常消息、日志、控制台输出、界面提示、埋点标签。

**不纳入词表**（元数据/文档）：`[Description]`、`[DisplayName]`、`[Obsolete]`、`[RequiresDynamicCode]` 等特性文本，以及 XML 文档注释——它们不经过查表路径，需要本地化时由管理端（如 Cube）另行处理。

两个守门脚本在 `run-tests.ps1` 与 CI 中执行：

| 脚本 | 校验内容 |
|---|---|
| `check-english-exceptions.ps1` | 异常 / 日志 / 控制台 / 界面提示 / 埋点标签中的运行时消息不得含中文 |
| `check-locales.ps1` | 各语言键集合与 `zh-Hans` 一致、占位符与格式说明符一致、无孤儿键（源码中已不存在的键） |

## 4. 下游组件接入

### 4.1 声明语言文件（推荐）

源生成器已随 `NewLife.Core` 主包以分析器形式分发，下游**无需额外引用生成器包**。用 `PackageReference` 引用主包时，包内 `build/NewLife.Core.props` 会自动把项目下的 `Locales/*.yml` 挂成 `AdditionalFiles`：

```text
My.Component/
├── Locales/
│   ├── zh-Hans.yml
│   └── zh-Hant.yml
└── My.Component.csproj
```

无需修改 csproj。若使用 `ProjectReference` 直连 Core 源码，或项目里的 `Locales` 目录另有用途，再显式声明/取消：

```xml
<ItemGroup>
  <!-- ProjectReference 场景：手动挂载语言文件 -->
  <AdditionalFiles Include="Locales\*.yml" />
  <!-- 同名目录另有用途：取消自动挂载 -->
  <!-- <AdditionalFiles Remove="Locales\*.yml" /> -->
</ItemGroup>
```

在组件项目下新建 `Locales/<culture>.yml`（格式与 Core 相同）。生成器会：

- 编译期校验占位符、格式说明符、重复键与语法；
- 生成 `LocalizationTable`，并通过 `[ModuleInitializer]` **自动注册**到 `Localization`；
- 生成内部 `L` 快捷入口，组件内可直接写 `throw new InvalidOperationException(L.T("English template", args))`。`L` 为 `internal`，不进公共 API；若组件自身已定义 `NewLife.L`，生成器自动跳过，避免类型冲突。
- 组件确实需要自己定义 `L` 又不希望生成时，可设 MSBuild 属性关闭：`<NewLifeLocalizationGenerateL>false</NewLifeLocalizationGenerateL>`。

> 生成器只处理 `Locales/` 目录下的 `.yml`，其他位置的 yml 不会被读取。旧框架没有 `ModuleInitializerAttribute` 时，生成器会补一个内部定义，行为一致。
>
> **本地源码联调**：分析器随 NuGet 主包分发，`PackageReference` 引用 `NewLife.Core` 时自动生效；若下游用 `ProjectReference` 直连 Core 源码，需额外把生成器项目作为分析器引入：`<ProjectReference Include="..\NewLife.Core\NewLife.Core.SourceGenerator\NewLife.Core.SourceGenerator.csproj" OutputItemType="Analyzer" ReferenceOutputAssembly="false" />`。
>
> **回归用例**：`XUnitTest.Core` 自带 `Locales/ta.yml`，等价于一个下游组件，用 `DownstreamLocalizationTests` 覆盖"声明 yml → 生成表 → 模块初始化自动注册 → `Localization.Translate` / `L.T` 生效 → 未注册语言回退英文"整条链路。
>
> **包消费回归**：根目录 `check-package-consumer.ps1` 会真实打包，并用临时项目仅通过 `PackageReference` + `Locales/*.yml` 跑通同一条链路；发布工作流在 Publish 前执行，失败即不发包。

### 4.2 异常与日志

| 场景 | 写法 | 是否需要改调用点 |
|---|---|---|
| 自定义异常 | `throw new XException("English template", args)` | 否，构造器自动翻译 |
| BCL 异常 | `throw new InvalidOperationException(L.T("English template", args))` | 是，替换消息 |
| 日志 | `XTrace.WriteLine("English template {0}", arg)` | 否，`Logger.Format` 自动翻译 |
| 自定义 Logger | 重写 `Format` 时调用 `Localization.TranslateForLog(format, args)` | 是，一行 |

### 4.3 覆盖 Core 译文

自动注册的覆盖策略按程序集类型区分：

- **应用（可执行程序集）**：默认 `overwrite: true`，应用 `Locales/*.yml` 中与 Core 同 key 的译文生效，"我的译文我做主"。
- **类库（下游组件）**：默认 `overwrite: false`，只补充新 key，Core 已有译文优先，避免任一依赖包在全局改写 Core 消息、结果依赖模块初始化顺序。

类库确需改写 Core 文案时，用 MSBuild 属性显式开启（`true`/`false`，优先于程序集类型的默认值）：

```xml
<PropertyGroup>
  <NewLifeLocalizationOverwrite>true</NewLifeLocalizationOverwrite>
</PropertyGroup>
```

也可在启动阶段手动覆盖（运行时新增语言、租户定制等）：

```csharp
Localization.Register(new CultureInfo("zh-Hans"), table, overwrite: true);
```

### 4.4 同一英文模板冲突

- Core 与下游使用同一英文原文：类库默认共享 Core 译文，应用默认覆盖；显式 `overwrite: true` 时覆盖。
- 两个下游组件使用同一英文原文且都覆盖：**后注册者生效**（由启动顺序决定）。
- 同一句话在不同语境需要不同译法：让模板措辞不同，不要依赖覆盖。

### 4.5 运行时新增语言（不引用生成器）

```csharp
Localization.Register(new CultureInfo("th-TH"), thaiTable);
```

适用于插件、租户自定义语言等场景，不需要重新编译。

### 4.6 下游升级与回滚

从旧版 Core 升级到多语言版本时，运行时消息的**源文由中文改为英文**，译文由本地化表按当前 UI 语言提供：

| 场景 | 升级后的行为 | 建议 |
|---|---|---|
| 中文操作系统 / `zh-CN` UI | 异常与日志自动显示中文（内置 `zh-Hans` 表） | 无需改动 |
| CI、Linux 容器、`en-US` | 显示英文源文 | 断言中文的测试改为断言英文，或临时设置 `Localization.Culture` |
| `InvariantGlobalization=true` | 具名区域性不可用，自动回退英文；下游生成的自动注册会跳过不可用区域性 | 不要在该模式下断言中文 |
| 下游组件自己的中文消息 | **不会自动翻译**，仍原样输出 | 先把消息改为英文源文，再补 `Locales/*.yml` |
| 需要保持旧版中文行为 | 可强制指定语言 | `Localization.Culture = new CultureInfo("zh-CN");` |

测试注意：

- `Localization.Culture` 是进程级全局状态，并行用例会互相干扰；改写它的测试应归入串行集合（本仓使用 `[Collection("GlobalState")]`）。
- 库测试优先断言异常类型、错误码或行为，不要依赖具体译文；必须断言文案时，显式设置语言。
- 滚动回退：临时把包版本固定到旧版即可恢复旧文案；长期方案是给下游消息补 `Locales/<culture>.yml`。

### 4.7 源生成器诊断与 MSBuild 开关

| 诊断 | 级别 | 含义 | 处理 |
|---|---|---|---|
| LOC001 | Error | yml 行格式错误 | 按 `"key": "value"` 修正 |
| LOC002 | Error | 同文件键重复 | 删除重复行 |
| LOC003 | Error | 占位符与英文原文不一致 | 让 `{0}`/`{1}` 集合一致 |
| LOC004 | Warning | 格式说明符不一致 | 保持 `:n0` 等与英文一致 |

MSBuild 开关（通过主包 `build/NewLife.Core.props` 传给分析器）：

| 属性 | 默认 | 作用 |
|---|---|---|
| `NewLifeLocalizationGenerateL` | `true` | 设为 `false` 时不生成内部 `L` 快捷入口 |
| `NewLifeLocalizationOverwrite` | 应用 `true`、类库 `false` | 显式指定是否覆盖 Core 同名译文 |

最低工具链：Visual Studio 2022 17.8+ / .NET SDK 8+（源生成器基于 Roslyn 4.8）。

下游完整接入步骤见[《下游多语言接入清单》](下游多语言接入清单.md)。

## 5. 语言清单与回退

| Culture | 回退映射 |
|---|---|
| `en` | 默认与兜底 |
| `zh-Hans` | `zh-CN` / `zh-SG` → `zh-Hans` |
| `zh-Hant` | `zh-TW` / `zh-HK` / `zh-MO` → `zh-Hant` |
| 其余语言 | 语言子标签相同即命中，如 `de-AT` → `de`、`pt-BR` → `pt`、`es-MX` → `es` |

当前仓库内置 31 种语言（每种 269 条已翻译词条，以 `zh-Hans.yml` 为准、英文为兜底）：

> 代码中的 `L.T` 词条允许暂时不在词表，运行时回退英文；翻译按语言增量补齐，`check-locales.ps1` 只校验已登记键集合的一致性。

| 区域 | 语言 |
|---|---|
| 东亚 | `zh-Hans`、`zh-Hant`、`ja`、`ko` |
| 东南亚/南亚 | `vi`、`th`、`id`、`ms`、`hi`、`bn` |
| 中东 | `ar`、`he`、`fa` |
| 欧洲 | `de`、`fr`、`es`、`pt`、`it`、`nl`、`pl`、`cs`、`sv`、`da`、`nb`、`fi`、`el`、`ro`、`hu` |
| 其他 | `ru`、`uk`、`tr` |

其余语言按需补充，缺失自动回退英文。

新增语言时把 `<culture>.yml` 放入 `NewLife.Core/Locales/` 即可，构建脚本与 CI 会用 `check-locales.ps1` 校验键集合、占位符与格式说明符。

## 6. AOT 与包体

- 语言表是编译期生成的**共享键表 + Deflate 压缩字节数组**，`switch` 分派、首次使用时解压建字典，无反射、无 `ResourceManager`、无 manifest resource 读取；
- 不引入运行时 NuGet 依赖；
- **按需构建**：只有真正用到的语言才解压并物化字典，英文（或未提供翻译）场景零分配。实测静态构造从 66.3 ms / 687 KB 降到 **1.0 ms / 8 KB**，英文热路径 301 ns → **22 ns**（中文约 118 ns），单语言首次解压约 0.1 ms；
- 每语言每 TFM 约 9 KB（实测 31 种语言使 net10.0 DLL 从 1,295 KB 增至 1,577 KB，较压缩前的 2,380 KB 减少约 34%；nupkg 10.9 MB，较压缩前 11.6 MB 同步下降）；NativeAOT 原生镜像同样按压缩后体积计入（本仓 31 种语言镜像 12.7 MB，较压缩前减少约 130 KB）；
- AOT 验证：`AotSmoke` 冒烟逐语种触发全部 31 张表（31/31 通过），确认裁剪器保留了全部词表且构建过程无反射；
- `InvariantGlobalization=true`：
  - 具名区域性**不可用**（`CultureInfo.GetCultureInfo("zh-CN")` 抛 `CultureNotFoundException`），`CurrentUICulture` 为 invariant，翻译自动回退英文；
  - 下游组件生成的自动注册会跳过不可用的区域性，**不会因模块初始化抛异常导致程序集加载失败**；
  - 该模式下同样跑通 AOT 冒烟 31/31。

### 6.1 体积优化评估（已收口）

31 种语言压缩后合计约 204 KB（每语言约 6~8 KB）。进一步压缩方案经实测均不划算，维持现状：

| 方案 | 压缩负载 | 相对现状 | 取舍 |
|------|---------|---------|------|
| 现状：每语言 Deflate + 按需解压 | 204 KB | — | 按需加载、无额外依赖 |
| 每语言改「位图 + NUL 分隔」 | 188 KB | −16 KB | 需改动已验证的二进制格式，收益约 1% DLL，不做 |
| 全语言合并 Deflate | 167 KB | −37 KB | 首次用到非英文语言即解压全部 600 KB 原始数据并建 8,277 条字典，放弃按需加载，不做 |
| 每语言 Brotli（q11） | 180 KB | −24 KB | Brotli 仅 netstandard2.1+/net6+ 内建，旧 TFM 需双路径，不做 |
| 全语言合并 Brotli（q11） | 140 KB | −64 KB | 同上，且放弃按需加载，不做 |
| 卫星程序集 | 主 DLL 回到 ~1.30 MB | 主 DLL −277 KB | 每语言 × 每 TFM 多一个 DLL，与"单 DLL"目标冲突，且需重新引入 ResourceManager 与裁剪处理，不做 |

> **嵌入资源不比 `Byte[]` 小**：两者都是原始字节 1:1 存储；源生成器只能输出 C# 源码，改用资源需额外构建期压缩任务，运行时还要资源名查找，AOT/裁剪更脆弱。
> 表中数字为压缩负载实测（zlib level 6 ≈ `CompressionLevel.Optimal`），差值直接反映到 DLL 体积；当前方案已处于"Deflate + 按需加载 + 无依赖"的实用下限。

## 7. 为什么不用 resx

- resx 默认产出**卫星程序集**（每语言 × 每 TFM 一个 DLL），与"单 DLL"目标冲突；
- 关闭卫星后，`ResourceManager` 默认不会从主程序集解析非中性文化，需要自写 `ResourceSet` 加载；
- 资源查找存在裁剪告警与 `MissingManifestResourceException` 风险；
- XML 噪音大、合并冲突多，翻译协作体验差。

resx 仍然适合**应用层**的 `IStringLocalizer`，与库级多语言是两种不同场景。
