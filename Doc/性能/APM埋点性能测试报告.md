# APM 埋点性能测试报告

> 测试日期：2026-10-10 ｜ 口径：单机微基准（BenchmarkDotNet，Release 模式）
> 基准代码：`Benchmark/TracingBenchmarks/` ｜ 原始输出：`BenchmarkDotNet.Artifacts/results/`

## 测试目标

量化两件事，为"是否/如何接入 APM"提供数据依据：

1. NewLife 原生埋点（`ITracer`，星尘侧）相对**完全不用 APM** 增加多少开销；
2. 在此基础上再叠加 **OpenTelemetry 输出**增加多少开销。

## 测试环境

| 项 | 值 |
|---|---|
| OS | Windows 10 (10.0.19045.6456 / 22H2) |
| CPU | Intel Core i9-10900K @ 3.70GHz，10 物理核 / 20 逻辑核 |
| 运行时 | .NET 10.0.12（X64 RyuJIT，x86-64-v3） |
| GC | Concurrent Workstation |
| 工具 | BenchmarkDotNet 0.15.8 |
| Job | LaunchCount=1、WarmupCount=3、IterationCount=10 |
| 内存诊断 | `[MemoryDiagnoser]`（Allocated 为每次操作的托管分配量） |

## 测试方法

**同一份被测方法体，只切换跟踪器档位**，保证各档严格可比：

| 档位 | 配置 |
|---|---|
| None | `tracer = null`。`Tracer?.NewSpan()` 被 `?.` 短路，代表"不用 APM" |
| Star | `DefaultTracer`。NewLife 原生本地聚合；`StarTracer` 的每片段路径与它相同（仅覆盖周期上报） |
| OtelNoListener | `OpenTelemetryTracer`，进程内没有任何 `ActivityListener` |
| OtelListener | `OpenTelemetryTracer` + 一个真实的活动监听者（`AllDataAndRecorded`） |
| Dual | `OpenTelemetryTracer { Inner = DefaultTracer }`，OTel 输出 + 星尘双写 |

四种真实埋点形态：**空埋点**（`using var span = tracer?.NewSpan("op")`）、**带标签**（匿名对象）、**嵌套两层**、**异常埋点**（`SetError`）。

## 测试结果

### 1. 单线程：每埋点开销

| 形态 | 无 APM | 星尘（Star） | OTel 无监听者 | OTel 有监听者 | 双写（Dual） |
|---|---|---|---|---|---|
| 空埋点 | 0.005 ns / 0 B | **290 ns / 384 B** | **5.2 ns / 0 B** | **257 ns / 696 B** | **607 ns / 1 168 B** |
| 带标签 | 0.002 ns / 0 B | 293 ns / 384 B | 5.3 ns / 0 B | 975 ns / 2 232 B | 2 175 ns / 4 216 B |
| 嵌套两层 | 0.29 ns / 0 B | 530 ns / 680 B | 11.5 ns / 0 B | 1 242 ns / 2 912 B | 2 709 ns / 5 320 B |
| 异常埋点 | 0.23 ns / 0 B | 2 896 ns / 2 848 B | 6.5 ns / 0 B | 3 110 ns / 4 560 B | 7 590 ns / 10 552 B |

> 无 APM 档位的 0.00x ns 是 JIT 把空操作消解后的循环开销，即**不接 APM 就是零成本**。

### 2. 优化前后对比（OTel 无监听者档）

| 版本 | 空埋点耗时 | 分配 |
|---|---|---|
| 优化前（`NewSpan` 无条件分配片段构建器） | 13.01 ns | 96 B |
| 优化后（无采集方直接返回空实现） | **5.22 ns** | **0 B** |
| 变化 | **-60%** | **分配清零** |

### 3. 8 线程并发（每操作摊算的墙钟时间）

| 档位 | 单线程 | 8 线程 |
|---|---|---|
| 无 APM | 0.005 ns | 0.85 ns |
| 星尘（Star） | 290 ns | **165 ns** |
| OTel 无监听者 | 5.2 ns | 15.4 ns |
| OTel 有监听者 | 257 ns | **57.6 ns** |
| 双写（Dual） | 607 ns | **217 ns** |

### 4. OpenTelemetry 采集器（第三方活动转为星尘埋点）

| 场景 | Mean | 分配 |
|---|---|---|
| 未挂采集器（进程内无任何监听者） | 4.56 ns | 0 B |
| 已挂采集器，但源不在采集范围内 | **4.69 ns** | 0 B |
| 已挂采集器，且源命中被采集 | **461 ns** | 640 B |

### 5. 星尘侧周期成本（`TakeAll`，每采样周期一次）

| 周期内累计埋点条数 | Mean | 分配 |
|---|---|---|
| 100 条 | 11.2 µs | 1.66 KB |
| 1 000 条 | 7.7 µs | 1.66 KB |

> 两者差异在测量噪声内（Error 分别为 2.19 µs / 0.61 µs）：成本只与**不同埋点名的数量**（本例 8 个）有关，与埋点条数无关——这是聚合模型的核心优势。按 60s 采样周期折算完全可忽略。

## 分析

**1. 不接 APM 是真正的零成本。** 埋点位置写法 `Tracer?.NewSpan(...)` 在 `tracer` 为 null 时被 JIT 消解（实测 0.005 ns / 0 B），因此"默认不启用"不会给现有代码带来任何负担。

**2. 一次普通星尘埋点约 0.3 µs / 384 B。** 对照真实业务：HTTP 接口 1–10 ms、SQL 数百 µs，0.3 µs 占 0.003%–0.03%；但对**纯内存高频操作**（缓存命中、协议栈每包）就是数量级差异。真正需要关注的是 **384 B/埋点**：10 万埋点/秒 → 约 38 MB/s 分配，会显著推高 Gen0 频率。（该值经 2026-10-11 优化后降至约 192 B/埋点，见文末「补充」章节）

**3. 带标签几乎不额外收费（星尘档）。** 293 ns vs 290 ns，因为 `BuildTag` 仅在采样（`TraceFlag > 0`）时序列化复杂对象，未采样时几乎零成本——这是埋点体系的一个良好设计。

**4. 异常埋点约 10× 于普通埋点（2.9 µs / 2.8 KB）。** `DefaultSpan.SetError` 会为异常**额外生成一条 `ex:Xxx` 埋点**，一次调用产生两份片段与多份异常字符串。异常风暴场景下的埋点成本不可忽略。

**5. OpenTelemetry 输出与星尘埋点同量级，但"带标签"明显更贵。**

- 空埋点：OTel 257 ns vs 星尘 290 ns（OTel 更快，分配 1.8×）
- 带标签：OTel **975 ns** vs 星尘 293 ns —— **3.3×**。原因是 OTel 语义要求标签变成活动属性，**必须**先序列化；星尘档在未采样时不序列化
- 异常：3 110 ns vs 2 896 ns（相差约 7%，可接受）

**6. 双写成本 = 两者相加，没有隐藏损耗。** 607 ns ≈ 257 + 290，说明装饰器实现未引入额外同步或重复序列化。

**7. 采集器：过滤几乎免费，命中后按活动收费。** 挂上采集器后，源不在采集范围内的活动仅 4.69 ns（与完全无监听者的 4.56 ns 持平）→ 白名单/排除清单策略本身不构成负担。命中后每个活动 461 ns / 640 B（其中活动自身仅 4.6 ns）——**640 B/活动**是主要风险：若第三方库每秒产生 10 万活动（如高频 Redis 调用），就是 64 MB/s 分配。

**8. 并发下无争用放大。** 8 线程时每操作摊算耗时**下降**（星尘 290→165 ns，OTel 有监听者 257→58 ns），说明埋点路径（对象池、`ConcurrentDictionary` 聚合、AsyncLocal）没有全局锁瓶颈，可随多核扩展。唯一的反向变化是无 APM 档 5.2→15.4 ns，来自 `HasListeners` 对共享静态结构的读取——绝对值仍可忽略。

## 优化建议

1. **（已实施）** 无采集方时不再分配片段构建器：13.01 ns / 96 B → 5.22 ns / 0 B，耗时 -60%、分配清零。
2. **高频低延迟路径按需埋点**：网络栈每包、缓存命中等场景建议用采样或条件埋点控制条数，重点盯 384 B/埋点的分配速率。
3. **异常路径节制**：异常埋点成本约为普通埋点的 10 倍（额外生成 `ex:` 埋点），避免在异常风暴路径上无差别埋点。
4. **采集器加限流**：为高频第三方源设置每周期条数上限或按源采样，避免活动转埋点带来的持续分配。
5. **OTel 输出控制标签大小**：标签会整串写入活动属性并随之导出，建议只放关键字段（星尘档在未采样时不序列化，可放心传对象）。
6. **（已实施）星尘档热路径减配**：Id/TraceId 延迟生成、去掉 `UtcNow.ToLong()` 装箱、缓存 `BuildSpan` 委托，单层埋点分配 504 B → 192 B。剩余约 192 B 为 `AsyncLocal` 上下文传播的固有成本，除非改变埋点上下文模型，否则降不下去。

## 补充：星尘档（DefaultTracer）分配归因与优化（2026-10-11）

口径：单进程、对 Release 构建产物用 `GC.GetAllocatedBytesForCurrentThread()` 逐段测量（与 `[MemoryDiagnoser]` 同源），非 BenchmarkDotNet 全量复跑；绝对值可比，但不含 BDN 的统计平滑。

**优化前，一次顶层空埋点 504 B，可精确拆分为 `Start` 384 B + `Finish` 120 B：**

| 来源 | 分配 | 说明 |
|---|---|---|
| `DefaultSpan.Current`（`AsyncLocal`）进入 / 还原各一次 | 104 + 88 B | .NET 固有：写值必然重建 ExecutionContext |
| `CreateTraceId()` 字符串 | 128 B | 未采样埋点也会生成 |
| `CreateId()` 字符串 | 88 B | 同上 |
| `Runtime.UtcNow.ToLong()` 装箱 ×3 | 96 B | `Utility.ToLong` 唯一重载形参为 `Object`，传 `DateTimeOffset` 必装箱；`ToUnixTimeMilliseconds()` 实测 0 B |
| `BuildSpan` 的构建器工厂委托 | 64 B × 2 次 | `GetOrAdd(name, k => OnBuildSpan(k))` 的 lambda 捕获 `this`，编译器无法缓存委托；`NewSpan` 与 `Finish` 各调一次 |

**优化三项（均不改变对外行为）：**

1. `DefaultSpan.Id` / `TraceId` 改为惰性生成（首次读取才创建，`Interlocked.CompareExchange` 保证并发读取一致），`Start` 不再无条件生成；未采样埋点因此不再产生这两条字符串。
2. `UtcNow.ToLong()` 全部改用 `ToUnixTimeMilliseconds()`（net45 缺少该 BCL 成员，库内以 `#if NET45` 扩展补齐）。
3. `BuildSpan` 的构建器工厂委托在构造函数中缓存为实例字段。

**优化后实测：**

| 场景 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 单层埋点（完整 `NewSpan` + `Dispose`） | 504 B | **192 B** | **-62%** |
| 两层链路（outer + inner 整体） | 867 B | **616 B** | -29% |

剩余的 192 B 全部是 `AsyncLocal` 上下文传播的固有成本。改用 `[ThreadStatic]` 会让埋点无法跨 `await` 传播；`Finish` 不还原 `Current` 会让后续埋点挂到已归还对象池的片段上——**「每次 NewSpan 零分配」在当前模型下不可达**。链路上父片段的 Id/TraceId 现在由首个子片段读取时生成一次，多级链路共享同一次生成，因此链路越长收益越明显。

## 已知限制

- 微基准为**单机、单进程、Workstation GC**；服务端 Server GC 与高并发下的分配/回收曲线不同，绝对值不可直接外推。
- 第 3 节的并发数据是**每操作摊算的墙钟时间（吞吐口径）**，不是争用下的单次延迟，也未给分位（P99）。
- 标签使用小型匿名对象；真实埋点若传 `IPacket`/大 JSON，序列化成本会明显上升。
- 埋点名固定为少数几个，**埋点名基数**对聚合字典与 `TakeAll` 的影响未单独测量。
- 未覆盖 net8 与 net10 的差异（同属一个运行时家族），也未覆盖 .NET Framework（已决定不为它提供 OpenTelemetry 输出）。
